# Story, timing, and narration

## Make the result the spectacle

Build around one coherent task. A useful arc is context -> intent -> real result ->
brief grounding -> more consequential capability -> usable deliverable -> conclusion.
Adapt this to the product rather than forcing every demo into seven scenes.

Open with enough context to orient the audience. An honest glimpse of a later
finished result can establish the payoff; never present it as the untouched starting
state. A prepared workspace may show descriptive context tabs, but should not begin
with an unproductive blank hold.

For an app-building story, prove functioning controls and independent use, not just
a newly styled report. Distinguish a local preview from actual hosting/sharing.
For an API/tool story, establish the enabling technology early only when verified;
do not turn the whole film into a tool-log lecture.

## Spoken copy

- Narrate directly what appears: "The map shows..." rather than "For this
  demonstration..." or "Let's look at...".
- Use measured future-looking language, not hype or unsupported predictions.
- Run a read-aloud pass for repeated nouns, adjacent sentence openings, redundant
  transitions, and words the user prohibited.
- Keep caveats honest and connected to the result, without making them the entire
  story. Do not delete meaningful uncertainty to make a closer punchier.
- Exact prompts are separate from narration. Label all pauses and screen directions
  as unspoken.

Count only spoken words. Rough rehearsal budgets are 120-150 words per speaking
minute, slower for technical names or dense evidence; ask or use the narrator's
actual pace when known. The checker flags high pacing but does not replace rehearsal.
Pause time reduces the speaking budget. Avoid filling runtime with long silence:
the Census reference's eight-second reveal pause was too long and became three.

## Timing

Create contiguous scenes with explicit frame boundaries. At 30 fps, 2:30 means
4,500 frames, not approximately 2:30 plus transitions. Count transitions and holds
inside the timeline. A fixed movie cannot adapt to a presenter's speed; separate
clips are an option if presenter-controlled pauses are required.

Include action duration, asynchronous result latency, deliberate dwell, and readable
time for the full submitted prompt. A script's nominal times are editorial goals;
use the actual recording/action timestamps to cut the film. Never crop a critical
label or speed up a gesture to preserve an unrealistic schedule.

## Versioning and variants

Use stable versioned filenames. Preserve the current approved master while making a
recut. Light/dark "same except theme" requires the same data, visible text, sequence,
timings, camera path, and pause lengths, verified separately. Prefer approved replay
of retained real responses if it provides deterministic parity; do not relabel it live.

## Approval artifact

Before recording, the user receives the whole click script, not only an outline.
Use a table for the timeline plus exact prompts/narration where that is more readable.
Record approval and the SHA-256 of the exact approved file in the plan. Revisions
invalidate that binding. Production notes may be separate to avoid needlessly
changing the approved spoken script.
